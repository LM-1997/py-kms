# KMS 客户端计数工具 — 设计与使用文档（P0 升级）

> 适用范围：本 fork 的客户端（`py-kms/pykms_Client.py`）及其打包产物（注入器 `pykms_Client.exe`）。
> 本文是 P0 四项升级的设计规范，实现完成后同时作为使用文档。

## 1. 背景与计数模型

自建正版 KMS 主机在独立客户端数低于门槛时拒绝激活（`0xC004F038`）。真实主机的计数规则（依据微软官方文档核实）：

- 计数按 **AppId** 维护：Windows 全系（客户端+服务器）共享一个计数器；Office 单独一个
- 请求中的产品族（KMS Counted Id）决定主机是否**受理**：不被主机密钥（CSVLK）覆盖的族直接拒收（RPC fault），且**不计入**
- 主机在响应中返回当前计数，**是否激活由客户端按自身门槛判定**（Windows 客户端 25 / 服务器与 Office 5）
- 主机只保留**近 30 天**的独立 CMID（Windows 最多 50 个、Office 最多 10 个），过期即衰减

由此得出工具的两个核心职责：**把计数补到门槛**（首次/衰减后），以及**让计数不衰减**（周期性续期）。

## 2. 升级总览

| # | 升级项 | 解决的问题 |
|---|---|---|
| P0-1 | 计数感知的自动停止与验证 | 盲发 N 个请求、成败要人工上主机查 |
| P0-2 | CMID 持久化池 | 每月计数衰减、需重跑、计数在 25↔50 间震荡 |
| P0-3 | 多族注入 | Windows + Office 要跑多次 |
| P0-4 | 健壮性 | 无超时挂死、bindNak 退出码为 0、响应可能读不完整 |

## 3. CLI 规范

| 选项 | 变化 | 说明 |
|---|---|---|
| `-m, --mode` | **变更** | 接受逗号分隔的多个产品族，如 `-m Windows10,Office2024`。默认仍为 `Windows10`。可用族见 `--help` |
| `-C, --repeat N` | 语义细化 | 每个族固定发送 N 个请求（字面语义，不自动停止）。未指定时进入**自动模式**（见 4.1） |
| `--cmid-pool FILE` | **新增** | CMID 池文件路径，默认当前目录 `pykms_cmid_pool.json` |
| `--no-cmid-pool` | **新增** | 禁用持久化，每次随机 CMID（旧行为） |
| `-t0, --timeout-idle` | **默认值变更** | 连接超时默认 **10 秒**（原为不限）。`0` 表示不限 |
| `-t1, --timeout-sndrcv` | **默认值变更** | 收发超时默认 **30 秒**（原为不限）。`0` 表示不限 |
| `-c, --cmid` | 不变 | 单请求测试用；与自动模式/池互斥时以显式值优先并告警 |

## 4. 行为规范

### 4.1 自动停止与验证（自动模式，`-C` 未指定时）

对每个族依次执行两阶段：

**阶段一：续期（renewal）**。对池中已关联到该族的每个 CMID 各发一个请求（刷新其 30 天窗口），无论计数是否已达标。目的：保持计数稳定、防止衰减。

**阶段二：补足（top-up）**。若续期后响应中的 `currentClientCount` 仍低于该族门槛，继续用**新** CMID 发请求，直到达标。

**停止与判定**：
- 计数 ≥ 门槛 → 该族成功，停止
- 安全上限：单族最多发送 `2 × 门槛 + 5` 个请求
- **停滞检测**：补足阶段连续 3 个响应计数无增长且仍低于门槛 → 判定失败并给出诊断：
  - 计数 = 2 × 门槛 → 提示"计数已达主机上限"（理论上不应发生在低于门槛时）
  - 其他 → 提示"主机未计入该族请求——所选族可能不被主机密钥覆盖，或主机计数行为异常"
- RPC fault → 立即终止该族（提示族不被覆盖），不影响后续族继续执行

**注意**：部分模拟服务器（含 py-kms 自带服务器）返回的计数不反映真实递增（固定返回 2×门槛）。对此类主机，自动模式会在第一个响应后判定达标并停止——这是正确行为，真实主机不受影响。

### 4.2 CMID 持久化池

**文件格式**（JSON，UTF-8，原子写入：先写临时文件再改名）：

```json
{
  "version": 1,
  "entries": [
    {
      "cmid": "01234567-89ab-cdef-0123-456789abcdef",
      "machine": "AB12CD34",
      "families": {
        "Windows10": "2026-10-17T03:00:00Z",
        "Office2024": "2026-10-17T03:00:01Z"
      }
    }
  ]
}
```

- `entries`：全局共享——一台模拟机（CMID+机器名）可关联多个族，与真实机器行为一致（同一台机器既有 Windows 又有 Office）
- `families`：该 CMID 已请求过的族及最近时间戳（信息性，用于续期排序与可观测性）

**取用规则**（对族 F 需要 CMID 时）：
1. 已关联 F 的条目，按最近请求时间**最旧优先**（续期语义）
2. 未关联任何族的既有条目（按加入顺序）
3. 新建条目（随机 CMID + 随机机器名，2–63 个 ASCII 字符）

**生命周期**：
- 每个成功请求后更新时间戳；运行结束时保存
- 文件损坏/版本不识别 → 备份为 `.bak` 后重建，并打印警告
- `--no-cmid-pool` → 完全随机，不读写文件
- 池文件是模拟身份映射，无敏感信息；删除即从零开始（下次运行重新爬计数）

### 4.3 多族注入

- `-m "Windows10,Office2024,WindowsServer2025"` 按顺序逐族执行 4.1/4.2 流程
- 每族独立判定成败，结束时输出**逐族摘要**（族名 / 达标计数 / 门槛 / 结果）
- `-C N` 对每个族各发 N 个（字面语义）
- 总退出码取各族最差值

### 4.4 健壮性

- **PDU 完整读取**：先读 RPC 头（24 字节），按 `frag_len` 补齐剩余——替代单次 `recv(1024)`，杜绝分片导致的解析错乱（bind 响应与激活响应同样处理）
- **bindNak**：退出码由 0 改为 1，并打印明确原因
- **默认超时**：见第 3 节；超时触发时给出可操作的错误提示（检查地址/端口/防火墙）

## 5. 退出码

| 码 | 含义 |
|---|---|
| 0 | 所有族达标（自动模式）或全部请求完成（`-C` 模式） |
| 1 | 硬错误：连接失败 / RPC fault / 响应解析失败 / bindNak |
| 2 | 停滞：计数低于门槛且连续不增长 |

## 6. 边界情况

| 场景 | 行为 |
|---|---|
| 主机计数已达标 | 阶段一仍续期全部已关联 CMID，然后直接判定成功 |
| 池为空（首次运行） | 全部走补足，计数逐请求爬升 |
| `-c` 显式 CMID + 多请求 | 沿用现有告警（同 CMID 不增计数） |
| `-c` 显式 CMID + 池启用 | 该请求用显式值，不记入池 |
| v4/v5 旧族 | 响应同样含 `currentClientCount`，自动模式照常工作 |
| 多族中某族 fault | 该族记 1，其余族继续 |

## 7. 测试计划

1. **单元**：族解析（含逗号列表）；池取用规则（续期优先→未关联→新建）；自动模式判定函数（给定计数序列 → 停止/停滞/继续）
2. **集成**（对本地 py-kms 服务器）：
   - 自动模式：固定 2×门槛的响应 → 阶段一后判定成功
   - 池持久化：两次运行 CMID 一致；跨族复用条目
   - 多族：一次运行两个族，逐族摘要正确
   - fault 注入（代理）：退出码 1 + 明确提示
   - 超时：对不存在的端口 → 10 秒内报错退出
3. **交付物**：exe 重建后重复集成测试
